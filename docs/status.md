## 保留限制

- 窗口刷新/重启后尚不能恢复运行中任务的前端进度订阅；数据不因此自动丢失，不能自动重发任务。
- 完整多窗口通知同步未实现；同步草稿日志也未处理多窗口同时编辑同一便签。普通目录不是安全沙箱。
- 保存汇总针对实际进入服务的调用，不能推断模型是否满足自然语言中要求的全部张数或内容。
- 强制退出/掉电、存储配额、卸载、异常重连、拼音组合输入和第三方皮肤还需针对性实机验收。
- 同 Host 进程只提供逻辑隔离，不保证崩溃、阻塞、内存耗尽或恶意代码隔离。

## 冻结决定与下一步

备忘录不增加富文本、附件、回收站、移动端、导出、侧边浮窗等功能。阻断实际使用的缺陷仍可修；其余限制保留为已知事项，不将所有待验项自动变成下一轮任务。

## 飞书 / super-agent 接入试验（2026-11-03）

用户授权尝试最小接入。当前结果是兼容性验证，未完成飞书收藏端到端，不启用新入口。

- 本机 desktop profile 加载 AppHub；superagent profile 加载 super-agent 及飞书 Source，二者不是同一工具作用域。
- superagent/src/app/sessions.ts 的 WORK_TOOLS 与 workOnly 显式限制继承工具；部署配置没有额外工具白名单选项。Runtime 通过内部 executorTools 注册 Worker 自身工具，未发现公开的业务工具注册入口。
- 复用上游 runtime.spec.ts 的隔离测试环境，将三个 apphub 收藏工具加入模拟的已安装工具，再创建授权 Worker；验证三个工具均未进入 Worker allow 列表，也未注册成其自身工具。Vitest：1 项通过、91 项跳过（按名称仅运行探针），不调用模型、飞书或真实数据库。临时测试副本已删除，上游源码未修改。
- 因此仅加载插件或补提示词不足以接通；不能通过 shell 直接写收藏库来规避工具边界，也不应把 desktop 的完整 owner 凭据交给 Worker。
- 真正接入需要两项明确适配：super-agent 的受限业务工具扩展，以及跨 profile 的专用认证调用。当前没有这些接口，不将两者伪装成简单配置。另一条路径是 AppHub 自己接飞书入口，但会新增消息接入责任，本轮未实施。

本轮未发送飞书消息、创建真实工单、调用付费模型、修改登录/权限或重启应用；不代表飞书当前在线。README 与 roadmap 的旧预览失败描述已按既有实机证据纠正。
